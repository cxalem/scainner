Research base: `origin/main@6a5710e060c885df13306bdb7263b8f8cfdfd5be`. Human gate
accepted 2026-09-02 through José's relay. Existing commit `473a5b5` is review

## Goal

Produce a draft x86_64 Windows installer from current main that launches without a
scanner, while preserving the macOS release and updater manifest. Call it an internal
Windows launch artifact, not a completed Windows port.

## Human gate (accepted 2026-09-02)

José relayed Alejandro's approval of all four decisions: (1) Design A, sequential
native builds with one reviewed SHA-pinned Tauri action and mandatory final manifest
inspection; (2) version-tag-only triggers, with unsafe input-less manual dispatch
removed; (3) unsigned Windows artifacts remain draft/internal pending a separate
Authenticode decision; and (4) recreate the workflow from current `origin/main`,
never ship `473a5b5`.

## Future implementation PR

Stream: `ws/windows-release-build`. Boundary: `.github/workflows/release.yml` only.

1. Recreate the Windows x86_64 job on current main; preserve the universal macOS job.
2. Pin checkout, pnpm, Node, Rust and Tauri actions to reviewed full commit SHAs.
3. Set workflow default `contents: read`; grant `contents: write` only to the macOS
   and Windows native jobs. Preflight and `verify-release` stay `contents: read`; the
   verifier receives only the built-in `GH_TOKEN`. Every checkout sets
   `persist-credentials: false`; updater secrets exist only on each Tauri step.
4. Trigger only on `v*` tags. A secret-free preflight job rejects any non-tag ref,
   removes exactly one leading `v`, parses `tauri.conf.json`, Cargo and desktop
   package versions, and requires all three to equal the result. Its tests include
   `v0.1.0` passing and a mismatched tag failing before native jobs can start.
5. Encode the job graph: macOS has `needs: preflight`; Windows has `needs: macOS`;
   `verify-release` needs both native jobs. Add concurrency keyed by tag so reruns
   cannot race a second release writer.
6. Label Windows output internal/test and state its exact supported surface: app shell
   only; no USB/Bluetooth or vehicle claim. Do not instruct public users to bypass
   SmartScreen.
7. Add an Ubuntu `verify-release` job with `needs` on both native jobs and read-only
   release access. Fetch the draft by exact tag through GitHub's API, then fetch its
   `latest.json`; never use `/releases/latest` for a draft.
8. Fail unless manifest keys `darwin-aarch64`, `darwin-x86_64` and
   `windows-x86_64` exist (confirm names against the pinned action), each with non-empty
   URL/signature fields, and top-level `version` equals the normalized tag. Require
   macOS DMG/updater/signature assets, both Windows MSI and NSIS installer classes, and
   only the Windows updater archive/signature actually generated by the pinned action
   (normally NSIS). Record installer SHA-256 values in release evidence, not the repo.

If the action cannot preserve all manifest entries, stop. Design B becomes a new
research/plan stream; do not add retries or handwritten merge logic ad hoc.

## Acceptance before merge

- Independent deployment-config review finds no mutable action tags or over-broad
  secret exposure.
- Static YAML/action validation passes; preflight proves one matching and one
  mismatching tag case; Windows PR CI is green on the exact commit.
- A protected test tag creates one draft, never a public release. The draft contains
  both macOS architectures, Windows x86_64, updater signatures and a complete manifest.
- On the authorized Windows machine, José verifies the recorded installer hash, then
  installation, launch, SQLite initialization, disconnected UI and uninstall. These
  results live in the PR/release evidence, not generated repo logs.
